# “研迹”学生—导师系统：页面与接口设计（V1.0）

## 1. 产品结构

### 1.1 全局入口

| 路由             | 页面     | 说明                              |
| ---------------- | -------- | --------------------------------- |
| `/login`         | 登录     | 手机验证码登录、微信登录          |
| `/account/bind`  | 绑定身份 | 首次微信登录绑定学号/工号和手机号 |

## 2. 五个关键页面规格

### 2.1 学生首页

首屏只突出一个主任务：本月成果。

必须显示：

- 当前年月和状态；
- 距离截止时间；
- 上次保存时间或最近提交时间；
- 导师反馈摘要；
- “填写/继续修改/查看结果”唯一主按钮；
- 待办任务和最近公告。

状态对应按钮：

| 状态                  | 主按钮         | 是否允许编辑 |
| --------------------- | -------------- | ------------ |
| `PENDING`             | 填写本月成果   | 是           |
| `SUBMITTED/REVIEWING` | 查看已提交版本 | 否           |
| `RETURNED`            | 根据意见修改   | 是           |
| `APPROVED/ARCHIVED`   | 查看成果与评分 | 否           |

### 2.2 学生成果提交页

页面分为三个区域：

1. 基本内容：标题、本月总结、具体成果、困难与问题、下月计划、自评进度。
2. 文档附件：主报告必填，支持Word/PDF/PPT；其他证明材料可选。
3. 提交确认：截止时间、是否逾期、保存草稿、正式提交。

交互规则：

- 草稿内容可存浏览器或独立草稿接口，正式提交才生成不可变版本；
- 上传文件先获取预签名地址，再直传对象存储；
- 文件完成校验后才能关联版本；
- 正式提交前必须二次确认；
- 重复点击或网络重试复用同一个 `Idempotency-Key`；
- `RETURNED`状态下顶部固定显示导师退回意见和所针对的版本。

### 2.3 导师审核工作区

采用“文档预览 + 审核面板”布局：

- 左侧：学生信息、本月填写内容、附件预览、版本切换；
- 右侧：历史意见、评分、审核意见、退回修改、审核通过；
- 顶部：上一个/下一个待审核学生；
- 通过或退回后自动进入下一份，提升集中审核效率。

退回时意见必填；通过时评分和意见是否必填由管理员规则决定。导师操作必须基于当前 `lock_version`，若学生或其他审核操作已改变状态，界面提示刷新，禁止覆盖。

### 2.4 院长学院概览

核心指标：

- 应交人数、已交人数、提交率；
- 逾期未交人数；
- 待审核与审核超时数量；
- 月报通过率；
- 导师平均审核时长。

下钻顺序：学院总览 → 专业/导师 → 学生 → 月报详情。月报详情为只读，并显示查看行为已记录审计日志。

### 2.5 管理员月度流程页

管理员按“草稿—预览影响人数—发布”创建周期：

1. 选择组织范围和年月；
2. 设置开放、T-7提醒、截止、审核截止、补交截止；
3. 预览应生成的学生数、缺少导师的学生和账号异常；
4. 修复异常后发布；
5. 发布时批量生成成果单和定时通知任务。

发布后，时间节点的修改必须展示影响范围，并记录审计日志。

## 4. API约定

- 基础路径：`/api/v1`
- 数据格式：JSON，时间统一使用ISO 8601和时区，例如 `2026-10-31T23:59:59+08:00`
- 身份认证：Web使用安全、HttpOnly、SameSite Cookie；移动端可使用短期访问令牌和轮换刷新令牌
- 分页：`page`从1开始，`page_size`默认20、最大100
- 排序：白名单字段，例如 `sort=-submitted_at`
- 幂等：正式提交、审核、导入、周期发布要求 `Idempotency-Key`
- 并发：修改成果状态时携带 `lock_version`
- 请求追踪：服务端返回 `X-Request-Id`

成功响应：

```json
{
  "data": {},
  "meta": { "request_id": "req_01..." }
}
```

错误响应：

```json
{
  "error": {
    "code": "SUBMISSION_STATE_CONFLICT",
    "message": "月报状态已变化，请刷新后重试",
    "details": { "current_status": "APPROVED" }
  },
  "meta": { "request_id": "req_01..." }
}
```

## 6. 核心事务边界

### 6.1 发布月度周期

一个数据库事务内完成：

1. 锁定周期并校验仍为草稿/计划状态；
2. 获取范围内有效学生及其主导师；
3. 为每名学生生成唯一成果单；
4. 写入周期发布事件到 `outbox_events`；
5. 更新周期状态并提交。

没有主导师的学生不静默跳过，应在发布预览中列为阻断异常。

### 6.2 学生提交新版本

1. 校验本人、周期时间、允许状态和 `lock_version`；
2. 校验所有文件已上传完成且属于本人；
3. 生成下一版本号并写入附件关系；
4. 更新当前版本、提交时间、是否逾期和状态；
5. 写状态日志与“待导师审核”事件；
6. `lock_version + 1`并提交事务。

### 6.3 导师审核

1. 校验当前导师快照、目标版本和 `lock_version`；
2. 校验状态迁移是否合法；
3. 写审核记录、更新状态/分数；
4. 写状态日志与学生通知事件；
5. `lock_version + 1`并提交事务。

## 7. 定时任务

| 任务           | 建议频率    | 作用                        |
| -------------- | ----------- | --------------------------- |
| 周期状态推进   | 每5分钟     | `SCHEDULED → OPEN → CLOSED` |
| 未提交提醒扫描 | 每小时      | T-7、T-3、T-1及逾期提醒     |
| 审核超时扫描   | 每小时      | 提醒超过审核期限的导师      |
| Outbox投递     | 每10秒      | 生成通知记录                |
| 通知发送       | 持续消费    | 微信/短信/邮件发送与重试    |
| 文件清理       | 每天        | 清理未关联的过期上传文件    |
| 统计快照       | 每小时/每天 | 加速院长和管理员看板        |

所有扫描任务都必须使用唯一业务键或数据库锁，支持多实例部署而不重复执行。

## 8. 验收场景

1. 学生手机号和微信均能登录同一账号。
2. 一个用户同时拥有导师和院长角色，切换后菜单及范围正确。
3. 周期发布前能发现没有导师的学生。
4. 学生重复点击提交只生成一个版本。
5. 学生提交后不能修改该版本；导师退回后才能提交新版本。
6. 导师不能审核其他导师名下学生。
7. 院长能查看本学院但不能查看其他学院，也不能改分。
8. T-7任务重复运行不会重复发送同一渠道提醒。
9. 学生更换导师后，旧月报仍显示原审核导师。
10. 管理员导入错误能够定位到具体行并下载错误原因。
